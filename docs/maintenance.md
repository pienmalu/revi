# 開発と公開

## 完成版の条件

既存機能の不具合は、公開前に修正して検証する。
後任への引き継ぎは、完成したアプリの保守と機能追加を対象とする。
既知の不具合を記録しただけでは、修正済みとは扱わない。

2026年9月24日時点では、本番公開前の確認が残っている。
同時操作と通知失敗の処理、PDF表示ライブラリの互換性、本番での一連の動作を確認し、見つかった不具合を修正してから完成を判定する。

## コードの構成

| 場所                                                | 役割                                               |
| --------------------------------------------------- | -------------------------------------------------- |
| `app/views/`、`app/components/`                     | 画面と部品                                         |
| `app/api/`                                          | 認証、入力の受付、HTTP応答                         |
| `app/lib/ingest.ts`、`analyze.ts`、`pdf-match.ts`   | PDF解析、版の照合、書き込みの取り込み              |
| `app/lib/workflow.ts`                               | WebとSlackに共通の確認処理と提出記録               |
| `app/lib/stage.ts`、`review.ts`                     | 一覧の分類と確認対象の計算                         |
| `app/lib/slack/`、`reminders.ts`                    | Slack連携と締切通知                                |
| `app/lib/repo.ts`、`db/`                            | DB操作、接続、スキーマの変更履歴                   |
| `app/lib/contracts.ts`                              | ブラウザとAPIで共有する通信の型                    |
| `app/lib/document-actions.ts`                       | 原稿・版の削除、移動、題名更新の判断とファイル操作 |
| `app/lib/client/use-document.ts`、`use-comments.ts` | 添削画面のデータ取得・更新と古い応答の破棄         |
| `app/components/PdfWorkspace.tsx`                   | PDF表示、選択、ズーム、タッチ操作                  |
| `app/lib/storage.ts`                                | 保存先の切り替えとファイルキーの検証               |
| `app/lib/errors.ts`                                 | HTTPやDBに依存しないエラー型                       |

DBとファイルの読み書きは、それぞれの境界に集める。
画面やSlackの処理に、版の判定や提出条件を複製しない。
Slackの操作受付は `slack/review.ts`、送信は `slack/notifications.ts` に分け、受付 → workflow → 通知の順に呼ぶ。
通信の型はDB操作を読み込まない。アップロード直後の版と、集計済みの詳細画面の版は別の型にする。
PDFの照合は候補の全版をまとめて取得する。取得・解析・比較のキャッシュはアップロード1回の範囲だけに持ち、候補追加時にも比較済みの版を再処理しない。

ローカルの実データは `data/`、秘密情報は `.env*` に保存し、Gitに含めない。
共有する設定は `.env.example` だけとする。
採用したアイコンは `app/icon.png` に置き、生成物と試作画像は `.gitignore` で除外する。
`scripts/seed-samples.ts` は空のローカルDBに架空の資料を3件作る。
既存データを消す処理は含めない。

## 動作確認

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm format:check
pnpm build
```

自動テストは一時ファイルとメモリ内DBを使い、実際のSlackには投稿しない。
本番の接続情報を渡さずに実行する。
ブラウザでは論文とスライドを開き、文字選択、範囲選択、コメント、版の切り替えを確かめる。
本番ではPDF受付から確認、提出記録までをテスト用チャンネルで通す。

## 公開前に解消する項目

| 項目     | 完了条件                                                                                     |
| -------- | -------------------------------------------------------------------------------------------- |
| 同時操作 | PDFの同時登録や提出報告の連打で、記録が重複したり版番号が衝突したりしない                    |
| 通知失敗 | 記録済みの操作を失敗と誤表示せず、再試行による記録の重複を防ぐ。定期処理の重複実行も検証する |
| PDF表示  | React 18向けの依存指定とReact 19の組み合わせを検証し、支障があれば依存関係を修正する         |
| 依存関係 | 脆弱性の修正版を適用し、残る警告は実際の呼び出しと影響条件を確認する                         |
| 本番環境 | 無料プラン、非公開のファイル保存、認証、データの保持、Slackとの通信を確認する                |

自動テストと本番ビルドが通っても、上表の確認が終わったことにはならない。
既存資料への同時登録、提出報告の連打、通知失敗、PDF保存失敗後の再送は自動テストで確認している。
新規資料の同時登録と定期処理の重複実行は、引き続き検証する。
一時DB・一時ファイル保存先を使ったChromeで、文字・範囲選択、コメント・返信・編集、保存失敗時の入力保持、ズーム、版切り替え、幅390pxの表示を確認した。
旧版の取得・保存応答を遅らせ、新版のコメント欄を上書きしないことも確認した。
コメントの初回取得中に投稿した場合も、既存のコメントと投稿内容が両方表示されることを確認した。
APIの返却値、原稿と版と書き込みPDFの削除、照合の一括取得とキャッシュを自動テストで確認した。
これらはローカルの確認で、本番環境と実際のSlackの接続確認は別途必要。
依存関係の監査では重大と高リスクは0件、中程度は3件だった。
残る警告はDrizzle Kit経由の開発サーバーと、間接依存の `uuid` に関するもの。
確認済みの `uuid` 呼び出しはv4で、警告対象はv3、v5、v6のバッファ処理である。

## 無料プランでの公開

Vercel Hobbyでアプリを動かし、Neon Freeに記録、非公開のVercel BlobにPDFを保存する構成を想定する。
無料枠は保存量や処理量に上限があるため、作成時にプランと利用条件を確認する。
有料プランへの変更は行わない。

1. 既存アカウントでVercel、Neon、非公開のBlobを用意する。
2. 本番の接続先にDBの表を作り、環境変数を設定する。
3. テスト用チャンネルで動作を確認する。
4. 利用者の承認後、研究室のSlackに導入する。

| 環境変数                | 用途                             |
| ----------------------- | -------------------------------- |
| `DATABASE_URL`          | Neonへの接続                     |
| `BLOB_READ_WRITE_TOKEN` | 非公開Blobへのアクセス           |
| `BASE_URL`              | 公開先のHTTPS URL                |
| `SLACK_BOT_TOKEN`       | ボットの認証                     |
| `SLACK_SIGNING_SECRET`  | Slackから届くリクエストの検証    |
| `CRON_SECRET`           | 定期処理の認証用に生成する合言葉 |

本番はSlackから直接受信するため、手元用の中継と `SLACK_APP_TOKEN` は不要。
[本番用の設定](../slack-manifest.yaml)の受信URLを公開先に合わせる。
[定期処理](../vercel.json)は日本時間の朝9時を指定している。
Vercelは設定済みの `CRON_SECRET` を認証ヘッダーに付けて呼び出す。

DBの表を作るコマンドは次のとおり。
本番専用の環境に `DATABASE_URL` を渡し、ローカル開発用の設定は切り替えない。

```bash
pnpm exec drizzle-kit migrate
```

このコマンドは既存データを転送しない。
版の重複を防ぐ移行では、同じ資料に同一PDFが複数あると停止するため、適用前に重複を調べる。
既存の版やコメントを自動削除して解消しない。
手元のデータを引き継ぐ場合は、更新を止めてDBとファイルをバックアップし、IDと保存キーを維持して移す。
転送用ツールは未実装で、引き継ぐ場合は公開作業に含める。

Webの表示名は「れび」、英語表記とパッケージ名は「revi」。
Webのアイコンは `app/icon.png` を使う。
Slackの表示名は両方のmanifestに記録してあるため、既存のSlackアプリを使う場合も設定を反映する。
Slackのアイコンは管理画面の「Basic Information → Display Information」で同じ画像を設定する。

## モノレポへの移行

管理者の許可後に `apps/revi` へ移す。
`nislab-monorepo` もNext.js 16とDrizzleを使っているが、pnpmは11系のため、依存関係とロックファイルを合わせる。
開発用ポート、Next.jsの参照範囲、アプリ専用の公開先も設定する。

DBは当初アプリ内に置き、共有が必要になった時点で `packages/database` へ移す。
同じNeonとBlobを使えばデータの転送は不要。
URLが変わる場合はSlackの受信先と `BASE_URL` を更新し、定期処理の実行元を一つにする。

Vercel Hobbyは個人の非商用利用向けで、組織所有リポジトリへの直接のGit連携には対応しない。
既存のCLI公開処理だけで無料利用を判断せず、移行先の契約を確認する。
[利用条件](https://vercel.com/docs/plans/hobby)と[Git連携の制限](https://vercel.com/docs/limits#connecting-a-project-to-a-git-repository)を参照。
